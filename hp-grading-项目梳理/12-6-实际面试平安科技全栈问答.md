## 一、自我介绍与情况

### 1. 结合在校学习、实习经历做一下自我介绍；实习技术栈是什么？

**名词：** 技术栈就是完成工作时用到的语言、框架、数据库和工具。全栈一般指能覆盖前端、后端及接口联调，但具体岗位要求可能不同。

**面试官在问什么：** 想了解你的成长经历、做过的事，以及技术能力是否符合岗位。没有确认的学校、年限、前端框架和实习岗位不要自行编造。

**参考回答：** “您好，我是【姓名】，在【学校/专业】学习期间，主要学习了【真实课程或实践，例如 Java、数据库、计算机网络】，也通过【真实项目】练习了接口开发和调试。实习期间我参与了慧批教育业务，主要使用 Java 和 Spring 处理后端业务，接触 MySQL、Redis 和 RabbitMQ；还用 Python 参与教学 Agent 工具封装和 RAG 开发。我独立开发过学情分析、AI 总结和周报，也和算法同事协作完成答题卡及教学 Agent 相关工作。前端方面我使用过【真实框架和工作内容，若没有就说明基础正在学习】。我希望继续提升完整业务交付能力。”

**准备：** 把每项写上真实熟练程度，准备一个你亲自修改的接口或页面；不要把接手维护说成从零搭建。

## 二、Kafka

### 2. 项目在什么场景使用 Kafka？生产者和消费者分别做什么？

**名词：** Kafka 是分布式事件流平台；生产者（Producer）发送事件，消费者（Consumer）读取并处理事件；Topic（主题）是消息分类；异步是发送方不必一直等待后续处理结束。

**考察点：** 是否真的理解业务链路和自己负责的部分。

**参考回答模板：** “在【真实项目】中，【业务行为】产生【事件】，生产者【服务】发送到【主题】，消费者【服务】读取后完成【处理】。引入 Kafka 主要是为了【实际需求，例如解耦、缓冲突发流量或供多个系统独立消费】。我负责【具体工作】，遇到【问题】时通过【已实施措施】处理。”

**项目边界：** 本资料确认慧批批改采用 RabbitMQ，而不是 Kafka；可如实说“慧批是 Java 把批改任务交给算法服务，算法处理后回传结果，项目已有 RabbitMQ 链路”。如果另一个项目确实使用 Kafka，补齐它的真实主题、生产者、消费者和本人贡献。Kafka 的相关知识可按下面题目回答，不能虚构项目。

### 3. Kafka 消费消息能保证顺序吗？

**名词：** Partition（分区）是主题的一条有序日志；offset（偏移量）是消息在分区中的位置；key 是消息键，可用于选择分区。

**参考回答：** “Kafka 能保证的是同一分区中消息的追加顺序和读取顺序，不能保证跨分区的全局顺序。如果同一订单的事件需要按顺序处理，可以用稳定的订单 ID 作为 key，让相关事件进入同一分区，并让消费者按分区顺序处理。还要考虑生产端并发和重试配置、消费者异步并行处理、失败重试和重复消费，否则读取有序也可能处理完成乱序。扩容分区可能改变 key 的分区映射，不能不做迁移设计就假定跨扩容仍有顺序。业务若要求严格顺序，应结合版本号和幂等校验。”

**考察点：** 区分“日志读取有序”和“业务最终处理有序”。

### 4. Kafka 整体架构有哪些组件？

**名词：** Broker 是 Kafka 服务节点；集群由多个 Broker 组成；Topic 包含多个 Partition；副本是分区的拷贝；leader 副本处理该分区主要读写，follower 同步数据；Consumer Group 是协作消费的消费者组；offset 记录消费位置；Controller 管理集群元数据和分区领导者等协调工作。

**参考回答：** “生产者把消息写到某个 Topic 的分区，分区分布在多个 Broker 上，并通过副本提高可用性。消费者以消费者组的方式订阅主题，组内分配分区并记录消费位置；不同消费者组可以各自独立消费同一批消息。新架构通常使用 KRaft 的 controller 管理集群元数据，老版本可能使用 ZooKeeper，实际要看版本和部署。副本与确认配置影响可靠性，并不是用了 Kafka 就一定不丢消息。”

**考察点：** 能否从消息写入、存储到消费画出整个流程。

### 5. Consumer 和 Partition 是什么关系？

**参考回答：** “在同一个消费者组中，同一时刻一个分区只分配给一个消费者，一个消费者可以负责多个分区。比如 3 个分区、2 个消费者，可能一个消费 2 个分区，另一个消费 1 个。不同消费者组之间互不排斥，可以分别读取同一个分区。组内有效消费并行度最多受分区数限制；如果有 3 个分区、5 个消费者，至少 2 个消费者空闲。”

**考察点：** 是否把“同组”和“不同组”区分开；实际处理并发还受应用线程设计限制。

### 6. Consumer 数量增加后会发生什么？

**名词：** Rebalance（再平衡）是消费者加入、离开或订阅/分区变化时，消费组重新分配分区。

**参考回答：** “增加同一消费者组的消费者后，组会发生再平衡，分区重新分配。例如 4 个分区原来由 2 个消费者各负责 2 个；增加到 4 个时，通常各负责 1 个；增加到 5 个时，至少 1 个空闲。具体分配取决于分配策略，增量再平衡可能只移动部分分区。再平衡期间可能影响消费，重复处理风险要用正确的 offset 提交和幂等设计处理；消费者增加不会自动增加分区。”

### 7. 为什么使用 Kafka 而不是线程池实现异步？了解线程池吗？

**名词：** 线程池预先管理一组线程和任务队列；解耦是让发送方和处理方不必直接绑定；削峰是把高峰任务暂时积压；回放是从保留的历史位置重新读取；持久化是将数据保存到持久介质。

**参考回答：** “线程池适合单个服务内部的异步工作，简单、开销小；但普通内存任务队列在进程退出时不能保证保留任务，也没有天然的跨服务独立消费和历史回放。Kafka 更适合跨服务事件分发、持续数据流、多个消费者组和可配置时间内的历史回放，但需要运维，也要处理重复消费、堆积和可靠性。两者可以一起用：Kafka 接收跨服务事件，消费者内部用有界线程池处理，但必须控制并发和 offset 提交，避免任务还没完成就提交。线程池要关注核心/最大线程数、队列容量、拒绝策略、任务类型和关闭方式；队列不是越大越好。选 Kafka 不代表线程池不能实现异步。”

**延伸：** 慧批实际使用 RabbitMQ，适合作业任务分派；不要声称它使用了 Kafka。见 [慧批 Q2 的 RabbitMQ 对比](12-1-慧批项目问答.md)。

## 三、MySQL

### 8. InnoDB 为什么使用 B+ 树？B 树和 B+ 树有什么区别？

**名词：** 索引像目录，帮助快速找到数据；B 树和 B+ 树都是多路平衡树，一个节点可以有多个分支；页是数据库读写的基本单位；叶子节点是树的最底层；范围查询如 `age BETWEEN 18 AND 25`。

**参考回答：** “InnoDB 常用 B+ 树索引：非叶子节点主要保存索引键和子节点指针，叶子节点保存索引记录；叶子页之间有顺序链接，适合按顺序和范围扫描。节点能容纳较多键，树通常比较矮，可以减少访问页的次数。B 树的数据记录可以出现在非叶子和叶子节点，B+ 树通常把记录集中在叶子，非叶子更适合做导航。InnoDB 聚簇索引的叶子保存完整行，二级索引叶子保存索引键和主键，取其他列可能还要按主键回表。它适合多种业务查询，但并不意味着所有存储引擎或所有索引都只能用 B+ 树。”

**考察点：** 将结构特点和磁盘页访问、范围扫描联系起来，而不是只背定义。

### 9. 联合索引 `(A, B, C)`，用 C、A 查询能否命中？

**名词：** 联合索引是按多列组合排序的索引；最左前缀指从索引第一列开始连续使用；索引下推（ICP）是在存储引擎读取索引时先检查可用条件，减少回表。

**参考回答：** “如果条件是 `WHERE C = ? AND A = ?`，SQL 里 C 写在前面不妨碍优化器使用 A。因为缺少中间的 B，通常可以用 A 定位连续索引范围，C 一般不能像 `(A,B,C)` 连续等值条件那样进一步直接缩小同一个连续查找范围；它仍可能用于索引下推或覆盖索引过滤。是否实际选这个索引，要看数据分布和执行计划。不同版本可能有跳跃扫描等优化，所以不能只凭最左前缀口诀判断所有情况。”

### 10. 查询使用 D、A 或 A、D，能否命中索引？

**参考回答：** “如果是 `WHERE D = ? AND A = ?` 或顺序相反的 `WHERE A = ? AND D = ?`，语义相同，优化器通常可以考虑通过 `(A,B,C)` 的 A 列查找，再对 D 做过滤。D 不在这个索引中，是否需要回表取 D 要看表结构和其他索引。它也可能选择 D 上的其他索引、组合策略或全表扫描，最终用 `EXPLAIN` 和实际数据确认。”

**注意：** 上述以 `AND` 和普通等值条件为例；如果是 `OR`，可用访问路径不同，不应照搬结论。

### 11. 包含最左列 A，为什么仍可能不走索引？

**名词：** 优化器估算不同执行方式的成本；选择性是条件过滤数据的能力；回表是从二级索引取主键后再查聚簇索引；统计信息描述数据分布。

**参考回答：** “有 A 不代表一定选这个索引。如果 A 的值覆盖大部分数据，走二级索引还要大量回表，优化器可能认为全表扫描更便宜。统计信息过期、数据分布倾斜、表很小、查询需要读取很多列，也会影响估算。另外条件写法可能让 A 无法用于有效的索引范围查找，比如对 A 做不匹配现有索引的函数运算，或字符串列与数字比较发生影响索引的隐式转换。先用 `EXPLAIN` 看选用的 key、访问方式和估计行数，再结合实际执行情况检查，不要把所有情况都归为‘索引失效’。”

### 12. 除全表扫描更快外，还有什么让索引无法有效使用？

**参考回答：** “常见情况包括：对索引列做函数或表达式运算，例如 `YEAR(create_time)=2025`，可考虑改成时间范围；对字符串列按数字比较可能发生隐式类型转换；`LIKE '%词'` 的前导通配符通常无法用普通 B+ 树做前缀定位；联合索引跳过中间列后，后续列不一定能继续缩小连续范围；`OR` 中某个分支缺少合适索引也可能改变访问路径。还要检查字符集、排序规则、索引是否存在或被设为不可见。函数索引、覆盖扫描、索引下推和优化器版本都可能改变结果，具体以执行计划为准。”

**资料：** [MySQL 联合索引](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html)、[索引使用说明](https://dev.mysql.com/doc/refman/26.10/en/mysql-indexes.html)。

## 四、Spring 事务与 AOP

### 13. `@Transactional` 原理和失效场景有哪些？

**名词：** 事务是一组需要整体提交或回滚的操作；AOP（面向切面编程）是在业务方法前后统一加入事务等行为；代理是包在目标对象外的一层对象；事务管理器负责开启、提交和回滚；传播行为定义调用其他事务方法时如何参与事务。

**参考回答：** “默认代理模式下，Spring 为符合条件的 Bean 创建代理。外部通过代理调用事务方法时，事务拦截器读取注解，使用事务管理器开启或加入事务，执行目标方法，成功时提交，符合回滚规则的异常出现时回滚。常见问题有：对象不是 Spring 管理的 Bean；同类内部直接调用绕过代理；异常被捕获后正常返回；默认规则下受检异常没有触发回滚；事务方法跑到另一个线程；数据库或事务管理器配置不正确；方法不可被所选代理方式拦截。具体还要看传播行为和配置。Spring 默认对 RuntimeException 和 Error 回滚，受检异常可以按业务用 `rollbackFor` 配置。”

**边界：** 异常被捕获并不意味着任何情况下都必定提交，事务可能已被标记 rollback-only；不同 Spring 版本及代理模式支持的方法可见性不同。

### 14. 为什么 private、final 方法可能导致事务失效？

**名词：** JDK 动态代理以接口调用为基础；CGLIB 通常通过生成目标类的子类实现代理；`private` 私有方法不能被子类覆盖，`final` 方法不能被覆盖。

**参考回答：** “在基于子类的代理中，Spring 要通过覆盖方法加上拦截逻辑；private 和 final 方法不能被覆盖，因此不能按这种方式拦截。JDK 动态代理则拦截通过代理接口发起的调用，所以需要区分实际调用路径；不能简单说所有 final 实现方法在任何代理下都失效。实际排查先看使用的代理类型、调用是否经过代理，以及 Spring 版本的注解支持范围。慧批资料提到 Spring Boot 2.3，面试中优先以该版本与项目配置为准，不把较新版本的可见性支持直接套上去。”

### 15. 同类中 A 无事务、B 有事务，A 调 B 如何让事务生效？

**参考回答：** “最清晰的做法是把 B 放到另一个 Spring Bean 中，A 注入该 Bean，通过它的代理调用 B。这样 B 可以作为事务边界。如果 A 和 B 的全部业务应该一起提交或回滚，也可以把 `@Transactional` 放到由外部代理调用的 A 上；但如果 B 配置了 `REQUIRES_NEW` 等单独传播语义，直接内部调用仍不会触发 B 自己的事务拦截。还可以通过获取自身代理或 AspectJ 模式实现，但要增加配置并明确适用场景。”

**简单例子：**

```java
@Service
class OrderService {
    private final PaymentService paymentService;
    OrderService(PaymentService paymentService) { this.paymentService = paymentService; }
    public void a() { paymentService.b(); }
}

@Service
class PaymentService {
    @Transactional
    public void b() { /* 数据库操作 */ }
}
```

**考察点：** 事务边界到底应该只覆盖 B，还是覆盖 A 和 B，取决于业务一致性需求。

### 16. 不使用编程式事务，有更简单的声明式方式吗？

**名词：** 编程式事务是代码显式调用事务 API 控制边界；声明式事务是通过注解或配置说明事务要求，让框架处理。

**参考回答：** “可以直接在外部通过 Spring 代理调用的 public 业务方法上加 `@Transactional`，这是常见的声明式方式。对上一题，如果 A 的整个流程都应在同一事务中，给 A 加注解通常最简单；如果只想让 B 有独立边界，就把 B 拆到另一个 Bean 并标注事务。具体要结合传播行为和异常规则。也可以通过 XML/AOP 配置声明事务，但一般注解更直观。”

### 17. 为什么同类内部调用会绕过事务代理？

**参考回答：** “外部拿到的是代理对象，调用 A 时可以经过代理；进入真正的目标对象之后，`this.b()` 是目标对象内部的普通方法调用，并没有重新经过代理，所以 B 上的事务拦截器没有机会读取注解并创建新事务。若 A 本身已通过代理开启事务，B 的数据库操作通常仍处于 A 的事务中，但 B 自己声明的传播行为、隔离级别等不会因这次内部调用被单独应用。AspectJ 编织模式不依赖同样的代理边界，行为不同。”

**资料：** [Spring AOP 代理机制](https://docs.spring.io/spring-framework/reference/core/aop/proxying.html)、[Spring 声明式事务](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)。

## 五、Agent 项目与技术选型

### 18. 开发 Agent 前调研过不同框架的特点和架构吗？

**名词：** 框架提供工具调用、状态管理等通用能力；架构是这些组件如何连接和协作；状态是任务执行过程中需要保留的信息。

**参考回答：** “做选型时我会先明确需求：工具调用、多轮状态、失败处理、人工介入，以及团队语言和运维能力。然后比较框架的抽象层级、状态持久化、控制流程、模型和工具接入、可观测性、学习与迁移成本。比如 LangChain 提供较高层的模型和 Agent 接口，LangGraph 偏向有状态的流程运行，也可以比较 Pydantic AI 这类方案。但我会区分实际做过的调研和事后学习，不能把所有框架说成都做过生产验证。”

**个人经历待补：** 实际开发前是否调研、对比哪些框架和测试过什么，现有资料无法确认。若没有，可说“当时主要沿团队现有方案实现，后来补充对比了这些选择”。

### 19. 为什么选择 LangGraph，而不是其他框架？

**名词：** `create_agent` 是 LangChain 的高层 Agent 构建接口，底层使用 LangGraph runtime；checkpoint 是持久化的运行状态；runtime 是执行流程的运行环境。

**参考回答：** “我们整理的方案使用 LangChain `create_agent` 构建常规 Agent 循环，底层由 LangGraph 运行；业务代码不需要手写节点和边。这样能沿用 LangChain 的模型、工具接口，同时为需要状态持久化和更细流程控制的情况保留扩展空间。选择还要考虑团队熟悉度、依赖和调试成本。其他框架也可能具备持久化和人工介入，应该按实际业务做对比，而不是说只有 LangGraph 能做。”

**项目边界：** 这回答描述确认方案；是否就是当时线上实际技术栈、是否由本人决定选型，需按代码和经历核实。模型选型和方案是与算法同事共同讨论。

## 六、Redis 和 AI

### 21. Redis 事务与 MySQL 事务有什么区别？

**名词：** Redis 的 `MULTI` 开始排队，`EXEC` 执行，`DISCARD` 放弃队列，`WATCH` 监控键以实现乐观锁；乐观锁是在提交时检查数据是否被别人修改；回滚是撤销已经执行的修改。

**参考回答：** “MySQL InnoDB 提供完整的事务机制，可以按规则提交和回滚，并通过日志、隔离级别和持久化配置保证相应的事务属性。Redis 的 MULTI/EXEC 把命令排队后连续执行，执行过程中其他客户端命令不会插入；但它不提供 MySQL 那样的回滚：如果 EXEC 执行时某条命令类型错误，其他命令仍可能执行，已执行的命令不会撤销。排队时发现语法错误可能导致整个 EXEC 被拒绝；WATCH 检测到键变化也会在执行前中止。Redis 持久性还取决于 RDB、AOF 等配置。业务需要复杂关系约束和失败回滚时通常更适合数据库事务。”

**资料：** [Redis 事务](https://redis.io/docs/latest/interact/transactions/)、[InnoDB ACID](https://dev.mysql.com/doc/refman/26.7/en/mysql-acid.html)。

### 24. 大模型推理参数是什么？为什么影响生成效果？底层原理是什么？

**名词：** Token 是模型处理文本的单位；logit 是模型对下一 token 的原始打分；概率分布是每个候选 token 被选中的概率；采样是按概率选择下一个 token；温度（temperature）调整概率分布的集中程度；Top-p 从概率最高的候选开始累积到指定比例，再在候选内采样；Top-k 只从得分最高的 K 个候选中采样；最大输出 token 限制生成长度；重复惩罚调整已出现内容的后续选择倾向。

**参考回答：** “模型会根据上下文给下一 token 打分，再把分数转换为概率；选出一个 token 后把它加入上下文，重复这个过程，直到结束或达到长度限制。温度会缩放分数：较低时高分候选更占优势，输出通常更稳定；较高时低概率候选更有机会出现，表达通常更多样，但也可能偏题。Top-p 和 Top-k 会限制参与采样的候选范围，重复惩罚可以降低重复，但过强可能影响正常复述。最大输出长度太小可能截断答案；它不等于输入上下文窗口。参数支持和具体实现因模型与服务而异，低温也不保证绝对正确或每次一致。实际调参要在固定样本上同时比较正确性、格式、延迟和成本，而不是只凭感觉。”

**例子：** 假设三个候选原始概率是 0.7、0.2、0.1；提高温度通常会让分布更平，后两个候选被选中的机会增加。下一次选词又依赖前面选出的词，所以早期的差异会影响后续整段输出。

**资料：** [Hugging Face 文本生成参数](https://huggingface.co/docs/transformers/main/en/main_classes/text_generation)。
