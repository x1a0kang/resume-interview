### Q23：Java 服务之间用 Feign 调用，和 Dubbo 有什么区别？RPC 是什么，比 HTTP 好吗？

**先说人话：** RPC 是“像调用本地方法一样调用另一个服务的方法”的调用方式；HTTP 是传输请求和响应的一套协议。两者不是同一层概念，不能直接说“RPC 一定比 HTTP 快”。Feign 把 HTTP 接口包装成 Java 方法调用，广义上也能称为基于 HTTP 的 RPC；Dubbo 是完整的 RPC 框架，既支持基于 TCP 的 Dubbo 协议，也支持基于 HTTP/1、HTTP/2 的 Triple 协议。

**本项目实际情况：** HP-Grading 使用 Spring Cloud OpenFeign：客户端声明目标服务与 GET/POST 路径，调用时仍是 HTTP 请求；本服务也提供供其他服务调用的 HTTP 接口。当前检查的 HP-Grading 仓库没有发现 Dubbo 依赖或使用入口，不能把 Dubbo 的能力说成项目现状。耗时较长的算法任务另用 RabbitMQ 异步分发，也不能说全部跨服务调用都经 Feign。

| 比较点 | Feign 调 HTTP 接口 | Dubbo RPC |
| --- | --- | --- |
| 定位 | 声明式 HTTP 客户端，服务端仍是 HTTP 接口 | 服务调用和治理框架，包含服务发布、发现、调用与多协议支持 |
| 接口表达 | URL、HTTP 方法、请求体和状态码可直接观察；Java 侧用接口隐藏请求细节 | 通常按服务方法与参数表达；实际传输取决于选用 Dubbo 私有协议还是 Triple |
| 优势 | 易与现有 HTTP 网关、浏览器调试工具和多语言服务对接；团队已有 HTTP API 时接入自然 | 内部服务方法契约清晰；协议、序列化、路由、负载均衡等治理能力集中；私有协议在合适场景可降低编码与传输开销 |
| 代价 | HTTP/JSON 场景可能有较大的报文与编解码开销；接口变更、超时、重试和错误映射仍需治理 | 增加框架与协议约束；私有协议对通用网关和异构客户端不如 HTTP 直接；迁移需处理服务契约和运维配套 |

**完整参考回答：** “RPC 的意思是远程过程调用：我在一个服务里调用另一个服务的能力，写起来像调用一个方法，但底层要经过网络，所以会有超时、失败和重试。HTTP 则是网络上请求和响应的协议。我们项目的 Java 服务调用主要用 Feign，把对方的 HTTP 接口声明成 Java 接口，调用时仍发送 HTTP 请求。Dubbo 是另一套服务调用框架，可以使用自己的 TCP 协议，也可以用基于 HTTP 的协议，所以不能把 Dubbo 简单等同于‘不用 HTTP’。如果已有 HTTP 接口、要接网关或不同语言的服务，Feign 比较顺手；如果内部服务之间调用很多，希望统一管理服务契约和通信协议，Dubbo 有优势。性能不能只看框架名字，要看协议、序列化、连接、请求大小和真实压测；而且无论哪一种，跨网络调用都必须处理超时、重试可能造成的重复操作，以及下游故障。”

**代码与外部依据：** [HP-Grading 的 Feign 客户端示例](../../hp/hp-grading/hp-grading-service/src/main/java/com/hp/grading/integration/HwIntegration.java)、[供内部调用的 HTTP 接口示例](../../hp/hp-grading/hp-grading-service/src/main/java/com/hp/grading/controller/feign/QuestionFeignController.java)、[Feign 依赖](../../hp/hp-grading/hp-grading-api/pom.xml)；[Spring Cloud OpenFeign 官方文档](https://docs.spring.io/spring-cloud-openfeign/reference/)、[Dubbo 协议概览](https://dubbo.apache.org/en/overview/mannual/java-sdk/reference-manual/protocol/overview/)。这里只说明当前代码中能核实的技术选型，不推断当时选择 Feign 的全部历史原因。

#### 追问：Python 写的 Agent/RAG 工具调用 Java 服务，该用 HTTP 还是 RPC？

**回答要点：** 如果 Java 已提供 HTTP API，Python 工具可直接通过 HTTP/JSON 调用，不需要使用 Feign；Feign 是当前 Java 侧的 HTTP 客户端。Python 调 Java 也可以选跨语言 RPC，例如双方定义同一份 `.proto` 契约并使用 gRPC；但需要 Java 新增 gRPC 服务端、Python 生成客户端，并处理部署、鉴权、超时与监控。Dubbo 有多语言方案，但不能因 Java 服务之间可能使用 Dubbo，就推断 Python Agent 已使用它。对于调用频率不高、主要获取作业/批改/统计数据的工具，沿用现有 HTTP API 通常改动较小；高频、严格类型契约或流式通信等需求，再按实际测量评估 gRPC。长耗时任务可以考虑现有 MQ 异步模式，不宜让一次同步工具请求无限等待。当前仓库不含用户所说的 Agent/RAG Python 实现，**实际已用什么客户端和协议待核对代码**。

**完整参考回答：** “我的 Agent 和 RAG 是 Python 写的，工具需要取 Java 业务服务的数据。如果 Java 已经有内部 HTTP 接口，Python 用 HTTP 客户端请求这些接口，拿 JSON 结果就可以；不需要让 Python 使用 Feign，因为 Feign 是 Java 客户端。Python 和 Java 也能用 gRPC 这种跨语言 RPC，但那要求双方维护共同的接口定义，Java 端也要提供相应服务。就这类查询业务数据的工具，我会优先考虑复用现有 HTTP 接口，重点做好身份校验、超时和错误处理。如果调用量和延迟数据证明 HTTP 方式成了瓶颈，再评估 gRPC。至于我们当前代码实际用了哪一种，我会展示 Python 工具的请求实现来说明，不凭架构猜测。”

**外部依据：** [gRPC Python 教程](https://grpc.io/docs/languages/python/basics/)、[gRPC Java 教程](https://grpc.io/docs/languages/java/basics/)。

#### 追问：都是内网调用，为什么不全用 HTTP/JSON？RPC 什么时候更优？

**纠偏：** “RPC 没有 HTTP 好”与“RPC 一定更快”都不准确。RPC 是调用模型，HTTP 是传输协议；gRPC 本身使用 HTTP/2，Dubbo Triple 也基于 HTTP/1 或 HTTP/2。真正有意义的比较通常是“普通 HTTP/JSON API + 客户端”与“gRPC/Protobuf 或 Dubbo 私有协议及其服务治理”。Feign 也已把 HTTP 调用封装为方法调用，并可结合 Spring Cloud 的服务发现、负载均衡等能力；不能说它完全没有治理能力。

**RPC 更可能占优的场景：** 内部服务之间存在大量高频、小报文调用，且压测确认 JSON 编解码、报文体积或连接管理是瓶颈时，二进制序列化和长连接可能降低开销；多个 Java/Python 服务需要共享明确的接口与字段类型时，gRPC 的 `.proto` 与生成代码有利于契约一致和演进；需要客户端、服务端或双向持续传输时，gRPC 或 Dubbo Triple 的流式模型更贴切；在大量内部服务中统一方法级路由、超时、负载均衡等策略时，完整 RPC 框架可减少各团队重复拼装。上述是**适用条件**，不是在本项目已证实的性能收益。

**HTTP/JSON 仍合适的场景：** 已有稳定的业务 API、调用量和延迟满足要求，工具主要查询作业与批改数据，或服务需要便于网关接入、人工调试和不同技术栈复用。内网环境只能减少公网访问方面的顾虑，不能自动让某种协议性能胜出；数据库查询、模型推理等耗时也可能远大于传输开销。是否更优要用相同业务请求比较端到端延迟、吞吐、CPU、报文大小与改造成本。

**完整参考回答：** “Dubbo 和 gRPC 的价值并不是证明 HTTP 不好。RPC 解决的是服务方法如何定义、调用和治理；gRPC 和 Dubbo Triple 实际也能跑在 HTTP 上。内网里如果服务调用非常频繁、每次数据很小，或者 Java 与 Python 需要严格共享一份接口定义、要做持续流式传输，gRPC 这类方案会更有吸引力；大量 Java 服务需要统一路由和调用治理时，Dubbo 也有价值。但如果我的 Agent 工具只是偶尔查询 Java 业务数据，Java 已有 HTTP 接口，数据库和模型处理才是主要耗时，改成 RPC 未必有可感知收益。应先看调用量和链路监控，再对同一批请求压测，而不是因为都在内网就一律换协议。”

**外部依据：** [gRPC 核心概念、流式调用与 deadline](https://grpc.io/docs/what-is-grpc/core-concepts/)、[Dubbo 协议概览](https://dubbo.apache.org/en/overview/mannual/java-sdk/reference-manual/protocol/overview/)、[Spring Cloud OpenFeign 功能](https://docs.spring.io/spring-cloud-openfeign/reference/spring-cloud-openfeign.html)。

### 补充 J1：requestId、version、幂等与消息确认分别解决什么问题？

**来自本人真实经历的事实：** 教师连续两次修改答案，第二轮重批先结束，第一轮后结束并覆盖第二轮结果。本人追日志后新增 version 校验；requestId、持久化状态和补偿是原有实现。约于 2026 年 3—4 月上线后，至 8 月离职未再反馈同类问题。此前偶发，一周未必一次，人工处理是再次手动重批，耗时几分钟。详见 [慧批 Q50](12-1-慧批项目问答.md#q50讲一次你亲自修复的线上故障旧批改结果为什么覆盖新结果)。

**回答组织：** requestId 用于关联请求与回调；version 在本案例中用于识别并拦截过时结果；重复投递是否重复产生副作用属于幂等问题；ACK 决定消息处理确认与后续投递。这些不能互相替代。实际幂等键、版本粒度及原子性尚未由本人确认，不以“加了版本号”宣称端到端 exactly-once。

**此前尚未回答的问题：** version 按题目、作业还是批改任务维护？何时生成和递增、如何传到算法并返回？如何保证比较与写入原子执行？如果两个回调同时读到旧版本，会不会都写成功？空版本、重复回调、异常落库后的 ACK 如何处理？

**后续讨论边界：** 条件更新、CAS、唯一键、事务等可以作为追问和改进方向，不能在未经代码或本人确认时写成当年已实现。旧 Q3 关于空版本及异常后 ACK 的审查结论保留，不能被本次“未再反馈同类问题”覆盖。
