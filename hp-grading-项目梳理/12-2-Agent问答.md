### Q6：Java 历史与 LangGraph checkpoint 如何配合实现多轮对话？

**完整参考回答：** “前端只访问 Java，由 Java 转发 Python。Java 保存用户问题和最终回答，负责历史展示；Python 使用 LangChain create_agent，底层运行在 LangGraph，通过 PostgreSQL checkpoint 保存 Agent 消息和执行状态。推荐 thread_id 等于 conversation_id，同一聊天保持稳定，每轮执行新建 run_id。下一轮只提交新输入，从 checkpoint 恢复摘要后的 state，不每轮重读 Java 全量历史。按钮仍走固定 Workflow，自由文本进入 Agent。”

**依据与边界：** 2026-10-23 [确认基线](agent-architecture-handoff.md) 与 [05 第 16.5—16.6 节](05-HP多角色对话Agent产品文档.md)。确认架构不等于已验证全部实现，更不代表具备进程重启自动续跑。

### Q7：Java 接口与 Python 工具如何复用既有权限关系？

**本人已确认：** 主要设计 Java 业务接口、封装 Python 工具。教师—班级、家长—孩子关系在原系统已经绑定，按身份及原有绑定关系确定可查询范围，不是本人新增一套关系权限系统，也不认领新的双层鉴权机制。实际工具数未统计，不沿用旧标题的“10 个”。

**完整参考回答：** “我的工作是把已有业务查询能力组织成适合 Agent 调用的接口，并封装成 Python 工具。教师能看哪些班、家长绑定哪个孩子，本来已有关系，我复用原系统的数据范围，不需要重新建设绑定关系。模型负责选择要查什么，工具与业务接口负责提供相应的批改和学情数据。”

**对原提问的解释：** 绑定关系与请求身份来源是两件事。这里只需核对原链路怎样确认传入的 teacherId 属于当前登录者，不能仅因使用前端 ID 就认定安全，也不能据此断言存在漏洞。本轮未审计认证代码，简历不新增安全成果；不把该核对变成要求本人新开发权限系统。

### Q9：流式输出与客户端断线如何处理？

**完整参考回答：** “Java Controller 创建 SseEmitter，把调用 Python 流式接口的任务提交到有界后台线程池，再立即返回 emitter。线程一边读取上游流、一边向前端推送并累计回答。客户端断开后，处理下游发送异常，但继续读取上游直到模型结束，再保存完整回答；用户回来可以查询最终结果。”

**边界：** 按新版 [05 第 16.5 节](05-HP多角色对话Agent产品文档.md)，只覆盖 Java 进程存活期间的客户端断线，不包括进程重启恢复、逐 token 持久化或跨实例实时续流。用户主动取消也不能与意外断线混为一谈；取消实现未在本轮确认，不写成果。

### Q13：有流式回答和多轮追问，一定需要 WebSocket 吗？

**完整参考回答：** “当前 Java 通过 SseEmitter 向前端推流，Python 返回模型输出。用户后续追问作为新的请求进入同一会话，由 Python 恢复同一 thread 的 checkpoint state。这里不需要为普通多轮对话引入 WebSocket 或挂起图执行。客户端断线后，这一轮可在原 Java 进程存活时继续生成并落库。”

**依据与边界：** [05 第 16.5—16.6 节](05-HP多角色对话Agent产品文档.md)。不声称具有事件游标重放或跨实例实时续流。

### Q14：模型追问后，原来的线程需要一直等待吗？

**完整参考回答：** “不需要。模型已经输出追问，这一轮就保存消息并正常结束。用户回答后经 Java 发起下一轮请求，Python 从同一 thread 的 PostgreSQL checkpoint 恢复状态。create_agent 底层使用 LangGraph；普通追问不需要 interrupt 挂起上一轮。”

**未来场景区分：** 真正要在后台长期运行或等待审核的业务任务，应独立建模任务状态；这不是当前普通聊天的实现，也不是已经完成的个人成果。

### Q15：断开连接、主动停止生成与进程重启是同一件事吗？

**已确认：** 客户端断开 SSE，不会自动终止原 Java 后台线程读取 Python 流；最终回答仍在该进程存活时保存。

**未确认/不宣称：** 主动取消涉及停止实际生成或工具执行，需要另看实现；当前方案不包含 Java 进程重启后的任务恢复，也没有逐 token 重放。因此不把“断线后完成回答”写成“断点续跑、跨实例恢复或可靠取消”。

**旧审核题处理：** checkpoint 已纳入确认方案，但审核暂停和恢复并非当前已确认能力。新版方案也不将修改标准答案、评分和重批作为 Agent 核心写工具。

### Q16：流式 Markdown 和 LaTex 输出尚未闭合时，前端如何显示？

**回答要点：** 后端收到模型增量后立即发送原始文本；前端累计 `rawText` 并按渲染节奏更新。未闭合的加粗、代码块或公式先降级为普通文本或安全占位，闭合后再交给 Markdown/公式渲染器。表格和大型结构化内容优先用明确事件或 JSON schema，而不是从不完整的 Markdown 中猜。渲染 HTML 前做白名单清洗，避免 XSS。

**完整参考回答：** “后端不用等一个 Markdown 段落或公式闭合才把 token 发给前端。前端持续保存原始文本，只是渲染时对未闭合的语法做降级：例如公式的结束符还没到，就先显示普通文本或占位；等公式完整再交给 KaTeX 一类的渲染器。表格和报告产物最好走结构化事件，因为流式 Markdown 中间态很难稳定解析。这样用户能及时看到输出，渲染也不会因为半个公式抖动或报错。同时模型内容进入 HTML 前要做安全清洗。”

**追问准备：** 缓冲用于视觉渲染，不等于延迟网络输出；详见 [11 第 5 节](11-简历指标与Agent-RAG问答总结.md)。

### Q17：模型流和前端事件协议是什么关系？

**参考回答：** “模型返回增量文本或工具调用，应用层负责组织成前端能消费的响应；当前 Java 负责把 Python 上游流通过 SseEmitter 转发。协议字段应该按实际实现解释，不能说用了某个框架就自动具备审核、取消、重连或事件重放。”

**当前口径：** 使用 create_agent / LangGraph 与 PostgreSQL checkpoint，摘要时通过 SSE 提示状态。旧问题列举的 text_delta、tool_status、approval_required 等名称只是协议讨论示例，不能在没有代码核对时认定全部存在于线上。

### Q18：聊天记录、中间步骤和后台任务怎样保存？

**完整参考回答：** “Java 的业务历史保存用户问题和最终回答；Python 的 PostgreSQL checkpoint 保存 Agent state，可能包含工具调用、工具结果、中间 AI 消息与摘要后的消息序列。它不是业务消息镜像，不直接用于前端历史展示。后台任务另需调度、重试和幂等机制，checkpoint 本身不会自动启动任务，也不保存每个 SSE token。”

### Q18-A：长对话何时摘要，摘要保存在哪里？

**完整参考回答：** “下一轮模型调用前由 SummarizationMiddleware 检查，达到阈值先同步摘要旧消息并保留近期消息，再生成本轮回答。压缩时经 Java SSE 提示正在压缩上下文，接受首字延迟。middleware 更新 state，PostgreSQL checkpointer 保存状态，不单独建摘要表。后续恢复同一 thread 的摘要后 state，再次摘要按旧摘要与当前消息滚动推进。60%/70% 只是候选示例，生产阈值与保留窗口需要压测。”

### Q18-B：两边存储如何避免并发和失败造成不一致？

**完整参考回答：** “Java 历史与 Python checkpoint 不是自动跨库原子提交，需要关联 conversation_id、run_id、message_id，设计幂等和补偿。同一 thread 的多轮执行要做跨实例协调，不能依赖单机锁或假设 checkpointer 自动排队。摘要失败、checkpoint 写入失败、回答生成后 Java 落库失败要分别处理。具体锁、队列、取消、重试与 SSE 协议尚未定案，不作为已完成成果。”

## 写入工具幂等：修改答案与重新批改的设计练习

> **事实边界：** 以下以“修改小空答案并重新批改”为假设场景，用于理解幂等和准备技术追问；不代表该写工具、人工确认、任务自动恢复或以下表结构已经上线。实际实现、个人贡献与故障案例需以代码和证据核实。本文的 PostgreSQL checkpoint 用于保存 Agent 状态；下文的 MySQL 是示例业务库，两者不是同一事务。

### Q19：什么是幂等？题目和小空有唯一 ID 就够了吗？

**参考回答：** “幂等指同一个业务操作重复执行，业务效果与执行一次相同，不要求代码物理上只运行一次，也不必然要求每次响应完全一样。题目 ID、小空 ID 只能定位修改对象，不能识别两次调用是否属于同一次修改。比如连续把答案覆盖为 A，答案本身可能保持不变，但如果每次都新建批改任务、增加修改次数或发送通知，整个操作仍不幂等。”

“老师先改成 A，后来主动改成 B，这是两个不同操作，即使小空 ID 相同也要允许各自执行。反过来，同一次改成 A 的超时重试应当被识别为同一个操作。”

### Q20：Agent 流程中什么时候可能重复调用写工具？

**参考回答：** “常见情况是业务服务已经成功写入，但响应在网络中丢失或超时；调用方不知道是否成功，于是按实际配置重试。也可能工具执行成功后，Agent 在保存相应状态前故障；从先前 checkpoint 恢复时，该步骤可能再次执行。后台批改还可能因消费者完成工作后未确认消息、进程崩溃等原因被重新投递。前端或用户也可能重复提交。”

**边界：** 这些是可能发生的场景，并非断言项目已配置自动重试、消息队列或重启续跑。LangGraph checkpoint 保存状态不等于保证外部写操作只执行一次，也不会自动启动中断任务。是否重跑取决于节点边界、恢复位置和实际配置。

### Q21：修改答案与重新批改拆开后，各自怎样判断幂等？

**参考回答：** “如果修改接口只是将指定小空的答案设置为 A，重复调用后答案和其他业务效果都不再变化，那么该操作通常是幂等的。但如果它每次新增历史记录、增加版本或发送通知，就要把这些效果一起考虑。重新批改接口如果每次都创建新任务，则不是幂等的。拆分可以使职责清楚，但不自动保证一致性；答案更新成功、发起批改前故障，仍可能漏掉批改。”

“不拆分也能做幂等：对一次修改使用稳定操作 ID，在同一业务库事务中记录操作、更新答案并创建唯一的批改任务。拆分时也需要保证两步可靠衔接。”

### Q22：用 MySQL 实现一次修改及批改任务去重，需要哪些数据？

**示例设计：** 假设答案和批改任务位于同一个 MySQL 数据库，实际表名和字段以项目为准。

| 示例表 | 主要字段 | 用途 |
| --- | --- | --- |
| `blank_answer` | `blank_id`、`answer`、`version` | 保存小空当前答案和版本。 |
| `answer_operation` | `operation_id`、操作身份或租户、`blank_id`、新答案或参数摘要、结果或 `job_id` | 记录一次业务操作；对适当作用域内的操作 ID 设置唯一约束。 |
| `grading_job` | `job_id`、`operation_id`、`blank_id`、答案快照、答案版本、`status` | 持久化批改任务；在业务规则允许“一次修改对应一个批改任务”时对操作 ID 设置唯一约束。 |

**区分三个 ID：** `blank_id` 找到被修改的小空；`operation_id` 识别一次修改及其重试；`job_id` 跟踪一次批改任务。用户主动发起新的修改或新一次重新批改，应生成新操作 ID；仅凭相同参数、同一小空或同一个会话不能判断两个请求是重复。

### Q23：操作 ID 从哪里来？重复、并发和失败分别怎么处理？

**首次发起：** 由可信的应用逻辑在首次可能执行写操作之前生成唯一操作 ID，并持久化或纳入可靠保存的待执行操作；人工确认、超时重试和恢复都复用它，不让模型每次重新生成。用户授权应绑定具体操作与参数，服务仍需按实际身份做权限校验。

**首次请求的同库事务：** 在事务内插入操作记录、修改答案、创建批改任务并记录返回的任务 ID，然后一起提交；任何步骤失败则一起回滚。不能把 HTTP 调用、模型调用或消息投递当作已被该数据库事务自动覆盖。

**重复请求：** 同一操作 ID 再次到达时，先核对身份及关键参数；参数不一致应拒绝。已提交的操作返回已有结果或任务 ID 及状态，不重复修改或建任务；若原请求仍在执行，可等待或返回处理中。失败且已回滚时，可按业务规则使用相同 ID 重试。

**并发请求：** 不能只“先查有没有，再插入”，两个请求可能同时查到不存在。依靠数据库唯一约束处理竞争；插入冲突后，在合适的事务边界读取已提交的记录，若尚未提交则等待或返回处理中。具体冲突处理以数据库和框架的事务语义为准。

**保留期限：** 去重记录至少覆盖允许重试、恢复和消息重投的时间窗口；记录清理后，相同旧 ID 再到达不再自动享有原有去重保证。

### Q24：批改任务如何处理重复执行、故障恢复和过期结果？

**参考回答：** “后台工作进程从任务表领取待处理任务，领取和状态变更要原子化；处理中要有超时或租约，进程故障后才能重领，并防止旧执行者在租约失效后覆盖新结果。任务保存答案快照和答案版本，确保知道批改的是哪个版本。结果写入以 job_id 去重，更新当前成绩时再校验答案版本；如果老师已修改为新版本，旧结果不能覆盖新答案的成绩，可保存为历史或标记过期。”

“任务唯一只保证不会创建多条同一任务，不保证后台代码或外部模型只调用一次。例如模型处理成功后，结果保存前进程崩溃，恢复时仍可能再次调用。外部服务支持幂等键时应传入稳定 ID；不支持时要考虑查询、对账和业务补偿，不能承诺外部物理执行恰好一次。消息和通知等副作用也要各自去重。”

**消息队列衔接：** 如果需要向 Kafka 或 RabbitMQ 发送批改消息，可在答案更新的同库事务里写入待发送事件（事务性 Outbox），再由后台投递；投递仍可能重复，消费者需按事件或任务 ID 去重。只在更新后直接发消息无法保证两步原子成功。

### Q25：面试中怎样简洁解释这套方案？

**方案型参考回答：** “对于会修改答案并触发批改的工具，我会给每次用户确认的业务操作生成稳定 ID，重试和恢复时复用。业务服务利用数据库唯一约束去重，并在同一个事务里保存操作记录、更新答案、创建批改任务。后台处理任务时按任务 ID 做结果去重，再用答案版本避免旧批改结果覆盖新答案。外部调用可能重复，需要下游幂等或对账支持。具体是否已落地，要以项目实现为准。”

**参考资料：** [AWS：幂等的写操作](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_prevent_interaction_failure_idempotent.html)、[AWS：事务性 Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)、[LangGraph：执行与检查点](https://docs.langchain.com/oss/javascript/langgraph/thinking-in-langgraph)。

## 面试练习时补齐的证据

1. **本人贡献：** 对应代码模块、提交/MR、设计决策和协作边界。
2. **运行链路：** 一条脱敏请求的输入、关键 ID、阶段状态、日志/Trace 与最终结果。
3. **指标：** 样本量、时间范围、统计单位、基线和复现实验方法；没有记录就明确为业务观察。
4. **Agent/RAG：** 仓库外代码位置、运行入口、Tool 注册表、会话消息存储、RAG 实际管线、权限拒绝用例、评测样本与部署状态。
5. **故障与取舍：** 准备一个真实失败案例，说明如何发现、定位、修复，以及哪些可靠性改进尚未完成。

## 开发难点与功能案例

### 案例 C：已有 Agent 项目里，怎样把模型能力接到教学业务工具

- **个人贡献已确认：** 公司在本人入职时已启动 Agent 开发；本人深度参与工具定义、Agent 规划与编排及相关开发。
- **适合回答的问题：** “Agent 为什么不能直接查数据库？”“如何决定工具粒度？”“为什么按钮 Workflow 和自由对话分开？”
- **技术难点：** 教师、学生、家长想完成的任务不同；原有 HP 与学情服务有大量细粒度接口。如果把底层接口全部交给模型，工具选择复杂、数据域容易越界，且统计事实会在模型层重复计算。
- **可以组织的解决路径：** 以业务目标定义较少的高层 Domain Tools，模型负责选择目标和补充条件，复用既有绑定关系和业务接口的数据范围；确定性查询与统计由业务服务完成。明确任务按钮可以直达 Workflow，自由文本才由 Agent 动态规划。具体 Tool 数量、状态节点和已实现的校验应以仓库外代码为准。
- **60 秒参考回答：** “公司已有 Agent 开发基础，我参与的重点是让它真正使用慧批业务能力。我们不是把数据库查询直接暴露给模型，而是围绕作业分析、题目和批改事实、教学资料等场景定义高层工具。模型可以决定下一步需要查什么，但教师能看哪个班、家长能看哪个孩子，复用原系统的绑定关系和数据范围，不认领额外新增的权限体系。对于按钮上目标已经明确的任务，用固定 Workflow 更稳定；自由文本再让 Agent 规划、追问和选择工具。我可以用一个教师讲评场景说明从用户目标到工具选择、权限校验和输出草案的链路，并明确指出自己定义或实现的部分。”
- **文档依据：** [05 的角色场景、入口与工具边界](05-HP多角色对话Agent产品文档.md)、[08 第 5 节](08-HP简历项目表述与事实边界.md)。仓库外 Agent 代码待补。
