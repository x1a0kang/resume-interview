模型、算法与存储各做什么

环节输入 → 输出是否需要模型
解析/OCR文件/页图 → 段落、标题、公式和图表原生文本提取可不需要；扫描件通常需要
分块章节与内容 → 完整教学单元规则优先，模型辅助可选
EmbeddingQuery 或 Chunk → 数字向量需要 Embedding 模型
BM25查询词与候选文本 → 关键词相关性排名统计算法，不需要大模型
Dense查询向量与文档向量 → 相似度排名生成向量需要模型，索引搜索本身不等于调用大模型
RRF多路排名 → 融合排名不需要模型
RerankQuery + 候选原文 → 相关性分数通常使用重排模型
生成用户问题 + 教材证据 + 业务事实 → 讲解需要生成模型

原文保存的两种合理方式

小型 RAG：向量数据库保存 chunk_id + 原文 + 向量 + metadata

HP 可选：
MySQL：权威原文、教学关系、版本和状态
ES：检索文本 + chunk_id + 必要过滤字段
VikingDB：向量 + chunk_id + 必要过滤字段
在线：候选 ID → 批量取原文 → 重排 → 生成

也可以在检索库冗余文本以减少回查，但仍要定义哪个版本是权威版本。最终上下文使用可追溯的原文，不能只有向量。

当前推荐候选

中文文本 Embedding 对照：BGE-M3、Qwen3-Embedding-0.6B。火山部署优先验证 doubao-embedding-vision-251215，1024 维可作为初始配置。

文本重排对照：BGE Reranker v2 M3、Qwen3-Reranker-0.6B。火山托管可验证 base-multilingual-rerank / doubao-seed-rerank。

这些是官方资料明确的候选，不是跨平台使用量排名或 HP 教材实测最佳。平台名称、参数和模型生命周期以实际使用的产品接口为准。
