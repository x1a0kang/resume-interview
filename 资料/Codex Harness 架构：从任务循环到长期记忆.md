# Codex Harness 架构：从任务循环到长期记忆

> 原文作者：小林。本文依据用户提供的正文归档；原文图片暂未提供，评论区不收录。
>
> 原文链接：https://mp.weixin.qq.com/s/ZxhhQlgzm7j7bfesSect4w

平时用 Codex，我们可能只会输入一句很简单的话：「帮我修改一下这个项目，完成后告诉我结果。」然后屏幕上就开始不断出现新动作：先读项目规则，再搜索代码、打开文件、修改内容、运行命令。命令失败后，Codex 还会读报错，换一种方法接着做。

但仔细想一下：大模型原本只会根据输入生成输出，既看不见电脑里的代码，也不能真的启动一个进程。为什么接进 Codex 之后，模型像突然长出了眼睛和手，还能连续工作十几步？答案藏在模型外面的 **Codex Harness** 里。

Codex 源码已经在 GitHub 开源：[openai/codex](https://github.com/openai/codex)。本文沿着一次任务的执行过程拆解其 Harness 架构，回答以下问题：

- Codex 由哪些部分组成，Harness 负责什么？
- 用户需求如何经过 App Server、Session 进入 Agent 主循环？
- 模型如何调用工具、工具结果又如何回到下一轮？
- 上下文如何组装、更新与压缩？
- 工具如何注册、路由与执行，审批、沙箱、并发与长进程如何配合？
- 会话如何持久化与恢复，长期记忆如何生成、检索与更新？
- Skills、MCP、Hooks 与多 Agent 接在哪一层？

## 01｜Codex 整体架构是怎样的？

### Harness 填补了模型与真实环境之间的空白

假设 Codex 里只有一个大模型。用户说「帮我修改项目」，模型最多生成一段回答；即使代码正确，它仍停留在文本中：文件没有改变，命令没有运行，任务也不会因一次失败自动发起下一次请求。

因此还需要有人：

- 将项目规则、代码片段和此前执行结果交给模型；
- 接住模型提出的动作，真正去读文件、改文件和运行命令；
- 记住任务进行到哪里，并判断何时继续、何时停止。

承担这些工作的就是 Harness。三个角色需要明确分开：

| 角色 | 职责 |
| --- | --- |
| 模型 | 决定下一步做什么 |
| Harness | 组织上下文、安排工具执行、收集结果并再次请求模型 |
| 执行环境 | 存放项目文件、运行命令与工具的真实环境 |

模型不会直接碰文件。它提出动作，Harness 将动作交给工具；工具在执行环境中完成操作并把结果交回 Harness；Harness 重新组织输入，再请求模型。模型给出的是一个下一步，Harness 把许多下一步接成一项完整工作。

### Harness 的五类职责

把一次任务放慢来看，Harness 至少要处理五类问题：

1. **接入与交互**：用户从哪个界面输入，运行过程怎样回到界面。
2. **会话与编排**：一项任务要请求模型多少次，下一步是否继续。
3. **上下文管理**：这次给模型哪些规则、历史和工具结果。
4. **工具与执行系统**：模型提出动作后由谁执行、权限是否足够。
5. **状态持久化与记忆**：任务关闭后如何恢复，过去经验如何被未来任务找到。

整体上，客户端与 App Server 位于上层；中间是会话状态、Agent 循环和模型客户端；一侧负责上下文与记忆，另一侧负责工具、路由与执行；底部保存会话历史、元数据和记忆产物。Harness 向模型服务发请求、接收回答或工具调用；模型、开放工具与命令运行方式均由配置决定；执行工具时还会按照权限策略处理审批和沙箱限制。

### App Server：统一客户端接入

Codex 不止一种界面：终端、IDE、桌面应用都可能提交任务，也都需要接收文字增量、工具进度、文件变更和审批请求。若每个界面各自实现 Agent 循环，同一任务在不同界面可能按不同流程执行，修复一个问题也得修改多套实现。

App Server 将界面发来的需求转交给 Agent 引擎，并把模型输出、工具进度和审批请求传回界面。它既可作为供客户端连接的服务，也可在同一进程中使用；核心职责不变：将用户要求传入，将执行过程传回。

Agent 并不是「请求进去、结果出来」的普通接口。一项用户请求可能连续产生几十个事件：客户端一边接收模型文字、一边显示工具状态；执行遇到审批时，服务还要反过来询问用户，等允许或拒绝后继续原流程。因此 App Server 负责的是持续的双向交互。

### 一项任务的闭环

输入先经由 App Server 进入会话；会话引擎准备本轮工作；上下文系统组织规则、环境和已有历史；模型客户端请求模型。模型可能先请求搜索代码，工具系统执行搜索并将结果写回历史。主循环发现任务尚未结束，便携带新结果再次请求模型；接着模型可能读取文件、修改内容或运行验证。

真正的主线是一个闭环：**准备上下文 → 请求模型 → 执行动作 → 得到反馈 → 再准备下一次上下文**。历史持续记录全过程；后台记忆会在满足条件时处理历史，为未来任务提供材料，而不会阻塞眼前任务。

## 02｜Agent 循环怎么运转？

### 为什么要多次请求模型

面对「帮我修改一下这个项目」的需求，第一次请求模型时，它并不知道项目包含哪些文件，合理动作可能只是读规则或搜索代码。工具返回结果后，模型才得到新的事实；第二次请求才可以据此判断应修改什么。修改完成后，验证命令又可能带来成功或失败信息，第三、第四次请求继续建立在这些反馈之上。

Agent 循环的本质不是模型神秘地连续思考，而是 **模型判断与环境反馈不断交替**。模型每次只基于当前输入输出，Harness 负责将前后多次请求串成一项工作。只要模型仍在请求工具，或仍有新输入等待处理，循环就不能停在当前响应上。

### 流式模型输出如何变成动作

模型返回的是流式事件，而不是一整段答案后再统一解析：

- 文字增量到达时，Harness 可以交给界面展示；
- 一个工具调用完整生成后，才进入工具分发；
- 响应完成事件到达时，Harness 更新该请求的状态和用量；
- 外层循环再判断是否仍有后续工作。

「模型正在输出解释」「模型已经提出完整动作」「本次响应已结束」是三个不同的时刻。半截工具参数不能执行，一段文字也不能误当命令。模型客户端处理连接和传输，主循环看到的则是统一的文字增量、工具调用和完成事件。

工具完成后，结果还必须带回原调用标识。若模型一次提出读取配置与运行命令两个动作，Harness 必须知道每段返回属于哪个调用；下一次请求才能看到调用与结果之间的对应关系，并判断哪一步成功、哪一步失败。

### Thread、Turn、Item 与 Session

一次模型响应结束后，用户任务未必结束。等待中的工具、用户补充输入和已完成动作，都需要保存在会话状态中，而非依赖模型自身记住。

- **Thread**：同一段会话，容纳多轮任务。
- **Turn**：每次用户输入发起的一轮工作；一个 Turn 可包含多次模型请求。
- **Item**：该 Turn 中产生的用户消息、模型回复、工具执行与审批记录。
- **Session**：程序内部的运行状态容器，保存历史、待处理输入与共享服务。

运行中的 Turn 还会记录仍在运行的任务，以及流程正等待用户输入、审批还是外部响应。

### StepContext：固定一步的运行视图

模型请求发出时，Codex 会捕获一份 StepContext，固定这一步使用的模型设置、环境视图、MCP 绑定、工具路由和项目规则。工具调用返回后，Harness 仍用这份请求上下文分发。

原因在于配置可能中途刷新。模型发送请求时工具目录里有工具 A，若工具返回前配置刷新、A 消失，而 Harness 按新目录解释调用，模型会收到「工具不存在」。StepContext 保证模型按哪份工具列表调用，Harness 就按同一份列表处理。

它固定的是本次请求的配置、工具列表和项目规则，不会冻结整个文件系统或外部世界；文件仍可能被用户或其他任务修改，外部服务也可能变化。

### 等待、取消与失败

工具需要审批时，Harness 会记录哪个操作在等待确认，并将审批请求发到界面；用户允许或拒绝后，再把答复交给对应操作。模型向用户提问时，也要记录正在等待哪个问题的回答。

用户追加输入通常先进入输入队列。已经发出的模型请求不会凭空多出新内容，主循环会在合适边界取走补充输入，让后续请求看到它。

取消则会触发取消信号并收尾当前任务，但已经写入的文件不会自动恢复；运行中的进程或子 Agent 也有各自生命周期，需要对应控制逻辑。

错误不能全塞进同一个「重试」框：命令退出失败可作为工具结果交给模型分析；连接模型服务中断时，Harness 可能等待重连或改用其他传输方式，取决于错误类型；无法继续处理的错误才结束本轮并清理运行状态。重新请求模型、重新执行工具、从历史恢复会话是三件不同的事，尤其已产生副作用的命令不能因模型连接重试而安全重跑。

### 何时结束循环

模型停止调用工具时，任务也不必立即结束。主循环还会确认：是否有用户刚补充的要求、是否有尚未处理的错误、停止前检查是否允许结束。用户追加要求或 Stop Hook 补入内容时，Agent 可能再执行一轮。

停下来并不等于需求一定完成。例如修完 Bug 只能说明文件变了，仍需看相关测试与验证结果。完整主循环是：从一次请求开始，经由工具获得新事实，处理等待与失败，再决定继续或结束。

## 03｜上下文怎么组织？

### 模型实际看到了什么

聊天框里只有一句话，Harness 发给模型的内容却更多：基础指令、当前任务与仓库约束、用户需求、项目规则、工作目录等环境信息、此前请求与工具结果、工具定义，以及（若启用）长期记忆导航。

工具定义必须进入上下文，因为模型不会凭空知道工具名与参数格式。上下文决定模型知道什么，工具定义决定模型当前能要求 Harness 做什么。

### 项目规则如何注入

代码仓库可能在根目录提供通用要求，在子目录提供更具体约定。Codex 围绕项目边界与当前工作目录查找规则文件，按层级组织找到的内容，并受到读取预算限制。根规则通常适用于全仓，离当前目录越近的规则通常越具体。

这不表示仓库内所有说明都会自动塞进模型：发现范围、候选文件、当前工作目录与读取预算均影响最终内容。Skills 和内部扩展也可从自己的入口补入说明或资源。

需要明确一条边界：写进上下文的规则可以影响模型怎样做，却不能直接扩大执行权限。项目文件即使写「允许访问某目录」，实际能否访问仍由 Harness 的权限策略与执行环境决定。文字指令解决行为选择，沙箱解决资源边界。

### 上下文基线与稳定前缀

若每次模型调用都追加相同规则和环境说明，上下文会迅速充满重复内容。Codex 会记录已向模型介绍过的规则与环境信息，作为上下文基线：首次请求提供必要环境说明，之后只在工作目录、设置等环境变化时补充变化部分。

这不表示后续请求只发送变化：之前的对话与工具结果仍会随请求发送，只是不再重复追加相同的环境说明。与 StepContext 对应，上下文系统组织这一步应看见的内容，StepContext 固定此次请求采用的设置、环境和工具视图。

稳定前缀还有助于模型服务复用前缀缓存。能否命中仍取决于服务与请求条件，但若 Harness 每一步重新排列前文，就难以保留这种机会。因此 Context Manager 不只控制长度，还要尽量保持不变信息稳定、让新信息正常追加、让变化状态得到更新。

### 长输出、历史规范化与压缩

工具结果会不断累积：文件内容可能很长，编译或测试日志也可能一次返回数万行。Codex 在记录工具输出时会应用限长策略，以控制进入模型历史的规模；不同工具和输出类型可采用不同预算与保留方式。模型看到的可能是受限结果，而非底层进程全部原始输出。

若信息不足，模型需要发起更精确的动作，例如读取指定范围、按关键词搜索或使用范围更小的命令重新获得证据。限长带来可控上下文，也可能丢掉暂时看不出价值的细节。

历史还要保持结构可理解：工具调用与结果通过调用标识配成一对。只剩调用，模型不知道动作是否完成；只剩孤立结果，模型不知道其对应什么。因此发送历史前，Codex 会做规范化：为缺失结果的调用补充中止等状态、按协议处理孤立结果、根据当前模型能力调整不支持的输入类型。补出的状态是为了表明调用没有正常完成，不是伪造成功结果。

即使单次输出被限长，长任务的历史仍会增长。Codex 跟踪使用量，在轮次开始前或运行中，根据阈值与继续条件触发压缩。总结式压缩可理解为一份交接说明：目标是什么、哪些已完成、确认了什么事实、尝试过哪些失败方法、后续要做什么。之后模型可凭摘要继续工作，不再携带早期每一步的完整输出。

压缩后 Harness 还会把必要初始上下文重新放在合适位置，因为任务摘要未必包含项目规则、环境和全部约束。压缩不是无损存档：它保住主线，却可能丢掉完整日志与局部代码细节。必须区分三个范围：当前模型窗口、Harness 维护的会话历史、长期记忆。上下文压缩服务于当前任务继续运行，不会自动将所有细节变成跨任务知识。

## 04｜工具调用怎么执行？

### 工具计划与可见工具

模型只有先看到工具名称、用途和参数结构，才能生成结构正确的调用。若把大量内部工具、MCP 外部工具和扩展能力全塞入每次请求，会占用上下文并增加模型选择负担。

因此每次请求前，Codex 都要形成工具计划：哪些工具直接展示定义，哪些在需要时再查找，模型调用后交给谁处理。计划会结合当前配置、模型能力、运行环境、已接入的 MCP 与内部扩展。

需要区分：系统中存在什么工具、此次请求向模型展示什么工具、Harness 最终能调用哪个执行器。这三者有关联，却不是同一份完整列表；所以同一个 Codex 在不同项目、模型或权限配置下，模型可用工具可能不同。

### Tool Router 与结果回写

模型输出的是包含工具名称和参数的结构化请求。Tool Router 解析请求，从当前工具计划中寻找对应处理器。工具不存在或参数非法时，返回相应错误，不能将模型生成的任意内容直接执行。

找到处理器后，Harness 将调用参数、会话信息和 StepContext 一起交给处理器。完成后，处理器封装带调用标识的工具输出。结果会走两条路：事件通道展示进展给客户端，Context Manager 将结果记入历史，供下一次模型请求使用。

### 审批与沙箱

读目录、改文件、访问网络和启动进程的风险与权限要求各不相同。执行类工具通常先走公共流程：按当前策略判断是否需要审批，再选择合适沙箱方式运行。

- **审批**回答「此动作是否需要额外获得许可」。
- **沙箱**限制「进程能接触哪些资源」。

二者不能混淆。用户批准某个动作不代表进程自动获得无限资源；沙箱执行失败也不代表系统会直接提升权限重跑。只有策略允许时，执行链路才可能请求许可或调整执行方式。

### Unified Exec：处理长时间进程

编译、测试或开发服务可能持续很久。若一次工具调用必须等待进程退出，Agent 无法在运行中观察新输出，也难以继续和交互式进程通信。

Unified Exec 将「一次工具请求」与「一个进程的完整生命周期」分开：负责启动、跟踪进程、收集输出，以及继续等待、写入输入与取消。第一次调用可先返回当前输出与进程标识，底层进程继续运行；后续调用使用标识读取新输出或发送输入，直到获得最终退出状态。因此，工具调用返回一段日志不代表进程已结束。

### 并发与执行环境

模型可能一次提出多个动作，Harness 需要决定能否并行。可并行工具拿共享通行证，可同时运行；需要独占运行的工具获得专用通行证后，其他调用等待其完成。该机制控制工具分发顺序，并不等于为整个文件系统加锁；工具若修改共享资源，仍要自行处理数据一致性。

工具还需要确定在哪运行：启动进程、读写文件等可交给 Exec Server，在本地或远程环境执行；MCP 工具请求各自连接的外部服务；内部控制工具直接在运行 Harness 的 Codex 进程处理。

App Server 连接客户端与 Agent 运行核心，传递用户请求与执行事件；Exec Server 连接工具与执行环境，负责进程和文件操作。二者职责不同。工具系统不是一个巨大的 Shell，而是多类处理器、权限策略与执行环境最终汇入同一个 Agent 循环。

## 05｜长期记忆怎么形成？

### 三种「记忆」

| 范围 | 用途 |
| --- | --- |
| 当前上下文 | 服务下一次模型请求，知道刚读了什么、改了什么 |
| 持久化历史与状态重建 | 重新打开原会话时继续此前工作 |
| 长期记忆 | 新会话中复用过去仍有价值的跨任务经验 |

三者不可混为一谈：压缩历史不是写长期记忆；会话保存后，新会话也不会自动读到全部旧聊天。

### 会话持久化与恢复

任务运行时，会话过程持续写入历史。当前本地实现使用 JSONL 保存事件历史；状态数据库可用时，再用 SQLite 保存便于查询的元数据。

重新打开原会话时，Harness 先还原已发生的用户消息、模型回复与工具结果，再恢复上下文基线、窗口用量等信息。恢复不只是重新展示聊天文字，而是让 Context Manager 知道下一步从哪里组织输入。

恢复也有边界：某些等待审批、交互对象或运行中的进程只存在于当时进程内；历史保存了什么，恢复才能重建什么。已发生的文件修改也不会因重放聊天而自动撤销或再执行。

### 历史如何提炼为长期记忆

App Server 会在带输入的新 Turn 成功启动、运行环境准备好后，尝试调度后台记忆任务。真正启动前还要确认：长期记忆已开启、当前会话不是临时会话或子 Agent 会话、状态数据库可用、账号剩余调用量高于系统阈值。任一条件不满足就跳过。因此长期记忆不是每轮结束立刻保存的固定步骤，也不保证默认启用或刚完成就进入下次请求。

写入分两个阶段。

第一阶段按会话来源、时间、空闲状态、记忆配置和数量限制筛选候选，并通过任务租约抢占处理资格。租约类似有时限的锁：一个后台任务取得后，其他任务暂时不能处理同一材料；即使中途异常退出，锁到期也会释放，后续任务仍可接手。模型从一次任务中提炼结构化原始记忆和任务摘要，目标是保留可复用偏好、有效步骤、失败教训等。没有值得长期保留的内容时也可以没有产出。

第二阶段进行跨任务整理。它先取得全局租约，选择第一阶段材料并同步到记忆工作区，再比较内容是否变化；无变化且现有产物通过检查时可跳过。需要更新时，Harness 启动专门整理 Agent，将经验整理为导航摘要、详细记忆、任务摘要和可复用步骤等文件。整理 Agent 是临时内部任务，会关闭再次生成或读取记忆、递归协作等能力，避免自我触发。

### 新任务如何读取和更新记忆

读取采用「先导航、再按需展开」。若记忆读取启用且已有非空摘要，扩展会将有限长度的记忆导航与使用说明注入开发者指令。模型先判断哪些过去经验可能相关；需要细节时，通过专用工具搜索详细记忆，并可继续读任务摘要与可复用步骤。

当前本地搜索主要按文字匹配，只返回命中位置周围一小段文本。这可避免将整份记忆读入上下文，但语义相近而措辞不同的内容可能搜不到。过去经验只是线索，项目代码和环境可能已经变化，模型仍必须回到当前文件与工具结果验证。

系统还会根据记忆引用等信号记录使用情况，再按时间窗口和数量上限挑选后续整理材料。长期未使用的原始材料可能清理，但已汇总内容仍要经过后续整理才会反映变化。使用次数仅说明被引用过，不构成自动事实校验。

## 06｜扩展能力怎么接入？

### 内部扩展机制

如果每增加一项能力都改主循环大量代码，Harness 会很快难以维护。Codex 提供扩展注册机制：扩展先登记自己会增加什么，以及应在什么时机运行。部分扩展为模型输入补充说明，部分增加工具，另一些则在会话启动、Turn 结束等时机处理。Harness 在准备模型输入、组装工具列表或到达相应生命周期时，再调用对应扩展。

记忆读取就是例子：准备请求时，记忆扩展补入记忆导航；模型需要详情时，同一扩展提供搜索和读取记忆的工具。这里是源码内部架构接口，不代表所有面向用户的插件、MCP 服务与 Skills 都遵循同一个公开接口。

### Skills、MCP 与 Hooks

- **Skills**：告诉模型某类任务应怎样做，并提供所需说明和资源。
- **MCP**：将外部服务工具接入，使模型可请求 Harness 调用。
- **Hooks**：让程序在指定时机介入，例如收到用户输入、工具执行前后或任务准备停止时。

也就是说，一个提供做事方法，一个接入工具，一个在特定时机执行处理。

### 子 Agent

子 Agent 沿用同一套运行架构：会话、上下文、模型循环与工具执行。多 Agent 在核心组件之上增加父子关系、消息传递与并发控制。父 Agent 可将部分调查任务交给子 Agent，子任务按配置继承相应上下文，独立运行后把结果传回；父任务收到新信息后继续自己的循环。

独立会话意味着运行状态分开，不等于文件环境一定隔离。父子 Agent 若指向同一工作目录，仍可能看到或修改相同文件；需要隔离时还要使用独立工作目录或相应环境策略。

## 面试回答模板

若被问「Codex 的架构是怎样的」，可以回答：

> Codex 的核心是在大模型外面加了一套 Harness。模型负责判断下一步，Harness 负责把判断变成真实行动。
>
> 整体可以分为客户端接入、会话编排、上下文管理、工具执行、状态与记忆五个部分。用户发起任务后，Harness 会在一个 Turn 里反复执行「组织上下文、请求模型、调用工具、写回结果」。中途需要审批或用户补充信息时先等待，收到答复后再继续。
>
> Context Manager 将规则、历史与工具结果整理给模型；Tool Router 找到相应工具处理器，再由执行流程按权限策略处理审批、沙箱和实际操作。Session 保存任务状态、负责上下文压缩与会话恢复；长期记忆则让经验跨任务复用。
>
> 主线就是：**模型决定下一步，Harness 让这一步安全执行，再把结果交给模型继续判断。**

## 核心结论

Codex Harness 的本质，是维护一个不断获得环境反馈的任务循环，让上下文、状态、权限、执行和记忆在正确位置发挥作用。无论接入 Skill、MCP 还是子 Agent，基本原理仍然是：**准备输入 → 请求模型 → 执行动作 → 接收反馈 → 决定下一步。**
